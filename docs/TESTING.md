## E2E Test Suite (Playwright)

The Playwright E2E suite (`e2e/`) covers eleven critical areas: **Authentication**, **RBAC**, **Editorial Workflow**, **Category/Tag Management**, **User Management**, **Accessibility** (axe-core runtime scan), **Responsiveness** (overflow/nav-toggle/column-hide/reflow @ 375/768/1024px), **Search & Filtering**, **Bookmarks & Reading History**, **Analytics Dashboard**, and **Security** (CSRF, rate-limit enforcement, XSS, security headers, malformed-body tolerance). Coverage was intentionally limited to high-risk areas, rather than the entire application. A total of **256 tests, all passed** — confirmed via a clean full run after two bugs were found and fixed in `users.spec.ts` (mismatched admin account data in the development database, and a Suspense-streaming race condition) plus a defense-in-depth fix for IP resolution in rate limiting (see the Security bullet point below).

- **Prerequisites**: `npm run dev` must already be running on port 3000 before `npm run test:e2e` (the `reuseExistingServer` configuration—does not start a new dev server if one already exists; the suite is not run automatically by the AI, but must be triggered manually by the user).
- **Target database**: Neon `dev` branch (same as the local `DATABASE_URL`). All test data is disposable (`e2e-*@test.newsportal.local` email addresses, article titles `[E2E] ...`, category/tag names `[E2E]...`) and is automatically deleted (`afterEach`/`finally` + `global-teardown.ts` as a safety net). Permanent test accounts (`farhan@newsportal{admin,editor,journalist,user}.com`) are used in read-only mode; their roles, passwords, and `isActive` status are never modified.
- **Rate limiting**: The Upstash rate limiter is active in the local `.env` file (`getRateLimiter()` set to 5 requests/15 minutes for registration + forgot/reset-password) — `auth.spec.ts` uses ~4 out of 5 slots in a single clean run. Do not run `auth.spec.ts` repeatedly within a 15-minute period, and avoid manual login/registration testing in the browser while the test suite is running.
- **Accessibility**: `accessibility.spec.ts` scans all public routes and the dashboard (by role) using `@axe-core/playwright`, following WCAG 2.1 AA. `color-contrast` is separated into its own pass-report-only category (never fails an assertion); other rules with a `critical`/`serious` impact cause the test to fail, while `moderate`/`minor` issues are logged in the test report without causing a failure. Run `npm run test:a11y` for an isolated scan.
- **Responsiveness**: `responsiveness.spec.ts` checks for horizontal overflow across the entire route inventory at 3 breakpoints (375/768/1024px, matching the project’s manual QA breakpoints), plus a specific regression test for the known `dashboard/users` grid→flex bug (boundary precision 1023/1024px), nav-toggle Navbar/DashboardNav/FilterPanel (precision boundaries 767/768px), column-hide in `dashboard/analytics`/`dashboard/review`, and reflow in `FeaturedSection`/homepage/`Pagination`. Found and fixed 1 actual overflow bug in `/dashboard/review/[id]` (action buttons do not wrap at 375px). Run `npm run test:responsive` for an isolated scan.
- **Search & Filtering**: `search.spec.ts` fills in the gaps in public functionality (300ms text search debounce, combinability of category/tag/date-preset filters, pagination with active filters, fallback for invalid or out-of-range `page` values, 2 variants of the empty-state text, and the public contract `GET /api/articles`). The `getSearchRateLimiter()` rate limiter (30 requests/minute per IP) is isolated per `describe` block via a fake `x-forwarded-for` header (`withFakeIp()` helper) — without this, the cumulative request volume for a single file could exceed 30/minute because Playwright does not send a unique IP per request. Run `npm run test:search` for an isolated scan.
- **Bookmarks & Reading History**: `bookmark-history.spec.ts` fills functional gaps in the dashboard (toggle bookmarks on/off, auto-track reading history, delete-per-item, “Delete All” via native `confirm()`, empty state, pagination, fallback for invalid `?page=`). Found and fixed bugs in the actual code: 5 paginated dashboard pages (`bookmarks`, `history`, `review`, `manage-articles`, `users`) were not using `parsePage()` and were still using the old manual `parseInt` pattern—all have been fixed. Run `npm run test:bookmark-history` for an isolated scan.
- **Analytics Dashboard**: `analytics.spec.ts` tests the summary statistics, the top articles table, and the weekly new users chart—previously, these were only checked for accessibility and RBAC; the content itself had never been tested at all. Since `getAnalyticsSummary()`/`getTopArticles()` are cached for 60 seconds and seeding fixtures via raw SQL never triggers `revalidateTag`, this test intentionally busts the cache via the Admin Override endpoint (for statistics and top articles) or by registering a new account on a specific fake IP (for the user graph, since its cache uses a separate `“analytics-users”` tag that is only invalidated by registration). Summary statistics are tested as before/after differences, not exact numbers, because the data is a global aggregate across all shared development databases. Run `npm run test:analytics` for an isolated scan.
- **Security**: `security.spec.ts` addresses gaps that were previously not covered by structured testing — CSRF (session cookie flags, anonymous requests always return a 401 on the 4 article-workflow routes), rate-limit enforcement, XSS (two separate mechanisms: `sanitize-html` for article content, React JSX escaping for titles — intentionally not combined into a single test), security headers (CSP/HSTS/etc., including two tests that intentionally assert the current permissive conditions), and malformed-body tolerance on 4 routes that do not use Zod. Found one actual security issue: IP resolution for rate limiting can be bypassed by changing the `x-forwarded-for` header per request — verified in local `npm run dev`. Fixed as a defense-in-depth measure via `src/lib/request-ip.ts` (centralized helper, prioritizes `x-vercel-forwarded-for` on Vercel, with the old fallback for dev), not as a “patch for a production vulnerability proven to have been exploited” — the initial finding was indeed from dev, not from an actual production exploit. The effectiveness of the fix in production has been verified directly (manual `curl` to `www.newsportal.my.id/api/auth/forgot-password` with various fake `x-forwarded-for` headers; `RATE_LIMIT` responses were received — Vercel’s edge network does indeed sanitize this header as officially documented). Run `npm run test:security` for an isolated scan.
- **Out of scope** (intentionally not tested here): SEO — has been manually verified and is scheduled for a separate automated test at a later date. Server-side file upload validation and 2 `npm audit` moderate findings are also out of scope for `security.spec.ts` — see CLAUDE.md for details.
